# 슬랙 자료 수집기 — 방식 결정 (2026-08-13)

`docs/api-spec.md`의 "남은 결정 #1"(슬랙 수집 방식) 확정 기록.

## 결론: 폴링

## 비교

| | 폴링 | Events API (실시간 웹훅) |
| --- | --- | --- |
| 동작 방식 | 서버가 주기적으로 슬랙에 "새 거 있어?" 조회 | 슬랙이 메시지/파일 생길 때마다 우리 서버로 push |
| 구현 복잡도 | 낮음 — HTTP 요청 하나 주기적으로 | 높음 — 서명 검증, URL 검증 핸드셰이크, 중복 전송 처리 |
| 로컬 개발 | 그냥 됨 | ngrok 같은 외부 터널링 필요 |
| Render 슬립 대응 | 서버가 잠들면 폴링도 멈춤. 그런데 스프링 스케줄러는 **앱이 깨어나 재부팅될 때 첫 실행을 즉시 돌리므로**, 누군가 사이트에 접속해 서버가 깨는 순간 밀린 자료가 자동으로 한 번에 수집됨 | 슬랙의 push 요청 자체가 서버를 깨우는 트리거가 됨. 콜드스타트 중 첫 시도는 타임아웃 나지만 슬랙이 자동 재시도해서 대부분 몇 분 내 처리됨 |
| 최악의 경우 지연 | 아무도 접속 안 하면 무기한 지연 (수동 "지금 수집" 버튼으로 보완) | 재시도 창을 넘기면 유실 가능 (드묾) |

## 결정 근거

- 이 프로젝트는 실시간성이 중요한 서비스가 아님 (개인 학습 기록장). 몇 분~몇 시간 지연이 치명적이지 않음
- 폴링 쪽이 구현·운영 부담이 훨씬 적음 (서명 검증/핸드셰이크/터널링 불필요)
- Render 슬립 문제는 두 방식 다 겪지만, "서버가 깨면 자동으로 밀린 자료를 즉시 수집"하는 스프링 스케줄러 기본 동작 덕분에 폴링의 단점이 걱정보다 크지 않음
- 부족한 부분(아무도 오래 안 들어온 경우)은 승인함 화면의 수동 "지금 수집" 버튼으로 보완

## 함께 정한 것

- 폴링 주기: 10분 (`@Scheduled(fixedDelay = ...)`, `initialDelay` 크게 잡지 않음 — 재부팅 시 즉시 1회 실행되게)
- 수집 채널: 여러 개 (콤마 구분 채널 ID 목록으로 설정, 채널 목록은 추후 확정)
- 매칭 로직: 메시지 날짜 == 판교 1반 일정 날짜, 단순 일치만 봄 (추정/키워드 매칭 없음). 안 맞으면 미매칭으로 승인함에 뜨고 관리자가 수동 relink
- 콜드스타트 자체를 없애는 것(UptimeRobot 등)은 이 결정과 별개 트랙 — 필요하면 나중에 따로 처리
