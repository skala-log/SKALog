# SKALog UI/UX 구성안 v1

> 기준 문서: [SKALog 기획서 v3](https://app.notion.com/p/3adc16705ac6806d8a17d95237db927f)
> 이 문서는 기획서를 화면으로 번역한 것이다. 기획서와 충돌하면 기획서가 우선하고,
> 이 문서에서 **기획서와 다른 제안**을 하는 부분은 16장에 모아 표시했다.

---

## 1. 이 구성안이 지키는 것

기획서 4장의 원칙 7개는 "좋은 말"로는 검증되지 않는다. 화면을 그릴 때 **위반 여부를 눈으로 판정할 수 있는 규칙**으로 바꾼다.

| 기획서 원칙 | 화면 규칙 (위반 판정 가능) |
| --- | --- |
| 1. 분류를 시키지 않는다 | 등록 폼에 **일정·폴더·태그 선택 필드가 존재하면 위반**. 대신 "어디에 저장되는지"를 고정 라벨로 보여준다 |
| 2. 입력은 제자리에서 끝낸다 | 등록 때문에 **URL이 바뀌면 위반**. 모든 등록은 인라인 폼 또는 바텀시트 |
| 3. 빈 화면을 보여주지 않는다 | 어떤 화면이든 **"없습니다" 한 줄로 끝나면 위반**. 빈 상태에는 반드시 대체 정보 + 다음 행동이 있다 |
| 4. 오늘을 기준으로 동작한다 | 진입 시 스크롤 위치가 **오늘이 아니면 위반** |
| 5. 모바일 2등 시민 금지 | 375px에서 **가로 스크롤·잘림·탭 실패가 있으면 위반**. 주요 액션은 화면 하단 1/3 안에 있어야 한다 |
| 6. 기능 추가를 성과로 삼지 않는다 | 신규 요소는 "이게 클릭 수를 줄이는가"에 답하지 못하면 그리지 않는다 |
| 7. 선택 기능이 필수 경로를 늘리지 않는다 | 파일 첨부가 **기본 폼에서 필수 필드처럼 보이면 위반**. 텍스트 버튼 한 개로 접어둔다 |

## 2. 정보 구조와 내비게이션

### 2.1. 화면 목록

```
[공개]
  로그인

[학생]
  홈(오늘)            /
  일정표              /timeline
  일정 상세           /timeline/:id
  내 기록             /records

[관리자]
  자료 승인함         /admin/materials
  일정 관리           /admin/schedules
```

### 2.2. 내비게이션 모델

기획서 6.1의 "사이드바 섹션화"는 데스크톱 형태다. 모바일 우선 원칙(원칙 5) 때문에 **모바일은 하단 탭, 데스크톱은 좌측 사이드바**로 두 형태를 쓴다. 같은 정보 구조를 두 배치로 표현하는 것이므로 항목은 완전히 동일하다.

| | 모바일 (<768) | 데스크톱 (≥1024) |
| --- | --- | --- |
| 주 내비 | 하단 고정 탭 3개 | 좌측 사이드바 240px |
| 항목 | 오늘 / 일정표 / 내 기록 | 학습: 오늘·일정표·내 기록 / 관리: 승인함·일정 관리 |
| 관리자 진입 | 헤더 우측 프로필 → 메뉴 | 사이드바 "관리" 섹션 (ADMIN에게만 렌더) |
| 본문 폭 | 100% - 32px | max 880px (관리자 화면은 1200px) |

**하단 탭을 고른 이유** — 핵심 시나리오가 "수업 직후 한 손으로 기록"이다. 상단 탭은 엄지가 닿지 않는다. 탭이 3개뿐이라 하단 바가 과하지 않다.

**사이드바를 섹션으로 나누는 이유** — 기획서 8.1의 확장 장치다. v1은 "학습" 섹션에 3개뿐이지만, 공지·출결이 들어올 자리가 그룹 안에 이미 있다.

### 2.3. 전역 슬롯 (우하단)

기획서대로 **v1에서는 아무것도 렌더하지 않는다.** 다만 레이아웃에서 우하단 `96×96` 영역을 다른 요소가 침범하지 않도록 비워둔다(모바일에서는 하단 탭 위 `right:16px, bottom:72px`). 콘텐츠가 이 자리를 차지하면 나중에 어시스턴트 버튼을 넣을 때 겹친다.

> FAB로 "빠른 기록"을 넣지 않는 이유: 어디서나 기록할 수 있게 하면 **"어느 일정에 넣을까"를 사용자가 골라야 한다.** 그 순간 원칙 1이 깨진다. 기록의 진입점은 언제나 "지금 보고 있는 일정"이다.

## 3. 디자인 토큰

Pencil/Figma에서 **변수(Variables)로 먼저 등록하고**, 이후 모든 요소는 raw 값 대신 변수를 참조한다. Tailwind v4의 `@theme`로 그대로 옮길 수 있게 이름을 맞춘다.

### 3.1. 컬러

출처는 SKALA 공식 사이트(`2026skala.co.kr`)의 실제 스타일시트다. 다만 그 사이트는 **다크 배경**이고 SKALog는 화이트 배경이므로, 색을 그대로 옮기지 않고 **관계를 뒤집어 배정**했다 — 그쪽의 딥네이비는 우리의 본문 텍스트가 되고, 바이올렛은 배경 그라데이션이 아니라 액션 색이 된다.

```
/* Neutral — 화면의 90%는 이 계열만 쓴다 */
--bg-app        #FAF8FF   앱 배경. 순백이 아니라 바이올렛 1% 틴트
--bg-surface    #FFFFFF   카드·시트 배경
--bg-subtle     #F5F3FA   구분 영역, hover
--border        #E6EAF0   1px 구조 경계 (그림자 대신 이걸 쓴다)
--border-accent #ECE6FF   강조 구분선, 선택된 영역 경계
--text          #111827   본문 · 17.7:1
--text-muted    #6B7280   메타 정보(날짜·강사·개수) · 4.8:1
--text-faint    #9CA5FF   비활성·플레이스홀더 (바이올렛 계열 연회색)

/* Primary — SKALA 바이올렛. 사용자가 누르는 것 */
--primary       #6C4DFF   기본 액션 (저장·다운로드·링크) · 5.1:1
--primary-hover #5A3FE0   · 6.5:1
--primary-soft  #F3F0FF   선택된 칩 배경
--primary-tint  #ECE6FF   선택된 칩 경계

/* Today — SKALA 핑크. '오늘'에만 배정한 유일한 강색 */
--today         #C81E4E   오늘 배지 텍스트 · 5.6:1
--today-vivid   #FF4378   오늘 좌측 3px 바, 점 등 비텍스트 도형 전용
--today-soft    #FFF1F5   오늘 행 배경

/* Mint — 브랜드 서명색. 진행 표현에만, 텍스트 금지 */
--mint          #2EE6C9   1.6:1 — 텍스트에 쓰면 위반
--progress      linear-gradient(90deg, #6C4DFF 0%, #2EE6C9 100%)

/* Semantic — 브랜드 그라데이션의 양 끝을 타입 구분에 재사용 */
--assignment    #4A37C7 / bg #F3F0FF    과제 배지 · 7.0:1
--note          #0F766E / bg #E6FAF5    노트 배지 · 5.1:1
--danger        #B91C1C                 삭제·반려 · 6.5:1
--success       #15803D                 승인·저장 완료 · 5.0:1
```

**색을 이렇게 아끼는 이유** — 매일 여는 도구는 색이 많으면 피로하다. 그리고 "오늘"이 이 서비스의 축(원칙 4)이므로, **가장 강한 색 하나를 오늘에만 배정**하면 어떤 화면에서도 눈이 먼저 오늘로 간다. 오늘 표식이 다른 배지와 같은 색이면 그 시그널이 죽는다.

**핑크를 오늘에 배정한 근거** — 임의 선택이 아니다. SKALA 사이트가 `#FF4378`을 캘린더의 **`live` 표식**에 쓰고 있다. "지금 진행 중"이라는 의미가 브랜드 안에 이미 배정되어 있으므로 그대로 계승한다.

**그라데이션은 화면에서 딱 한 곳** — 23주 진행 바(홈 오늘 스트립, 내 기록 요약 스트립). `#6C4DFF → #2EE6C9`는 SKALA의 서명이지만, 유틸리티 앱에서 여러 곳에 쓰면 값싸 보인다. 한 곳에만 있으면 브랜드 모먼트가 된다.

### 3.1.1. 색 사용 금지 규칙

프로토타입 검수 시 이것만 확인하면 색이 무너지지 않는다.

- 바이올렛은 **누를 수 있는 것에만.** 장식용 바이올렛 면적을 만들지 않는다.
- 핑크는 **오늘 외에 어디에도 쓰지 않는다.** 알림·강조·에러에 쓰면 오늘 시그널이 죽는다.
- 민트는 **텍스트·아이콘·경계선에 쓰지 않는다.** 진행 바 채움색으로만.
- 그라데이션은 진행 바 1개. 버튼·카드·헤더에 쓰지 않는다.
- 바이올렛 텍스트에는 밑줄을 넣지 않는다(방문한 링크로 오인된다). 링크는 색 대신 `↗`·`↓` 아이콘으로 구분한다.

### 3.2. 타이포그래피

**SUIT**를 기본 폰트로 둔다. SKALA 공식 사이트가 쓰는 폰트이고(`cdn.jsdelivr.net/gh/sun-typeface/SUIT`), 색과 함께 브랜드 일관성을 만드는 두 번째 축이다. 현재 `index.css`의 Pretendard fallback을 교체한다.

```css
@import url("https://cdn.jsdelivr.net/gh/sun-typeface/SUIT@2/fonts/variable/woff2/SUIT-Variable.css");
font-family: "SUIT Variable", system-ui, -apple-system, sans-serif;
```

> 대안은 Pretendard다. 장문 본문 가독성은 Pretendard가 근소하게 낫지만, SKALog의 텍스트는 대부분 짧은 제목·메타라 차이가 드러나지 않는다. 브랜드 일치를 택한다. **두 폰트를 섞지는 않는다.**

| 토큰 | 크기/행간 | 굵기 | 용도 |
| --- | --- | --- | --- |
| `display` | 24 / 32 | 600 | 화면 제목 (데스크톱) |
| `title` | 20 / 28 | 600 | 화면 제목 (모바일), 일정 상세 과목명 |
| `heading` | 17 / 24 | 600 | 카드 제목, 섹션 제목 |
| `body` | 15 / 24 | 400 | 본문, 목록 항목 제목 |
| `label` | 14 / 20 | 500 | 버튼, 탭, 폼 라벨 |
| `meta` | 13 / 18 | 400 | 날짜·강사·개수 |
| `badge` | 12 / 16 | 600 | 배지, 주차 표기 |

본문을 15px로 잡은 것은 모바일에서 한글 2줄 이상이 자연스럽게 들어오는 하한선이다. 14px은 수업 중 흔들리는 상황에서 읽기 부담이 있다.

### 3.3. 간격 · 형태 · 모션

```
spacing   4 8 12 16 20 24 32 48        (4의 배수 고정)
radius    control 8 / card 12 / sheet 16 상단만 / pill 999

          예외: 바텀시트·드롭다운만 0 8px 24px rgba(0,0,0,.12)

```

## 4. 공용 컴포넌트

기획서 8.1의 "공용 컴포넌트 3종"을 실제 필요한 6종으로 확정한다. **이 6종 밖의 새 패턴이 필요해지면, 그건 화면 설계가 틀렸다는 신호로 본다.**

### 4.1. Card

홈 그리드와 상세 섹션의 기본 단위.

```
┌─────────────────────────────────┐
│ 카드 제목            [보조 액션] │  ← header: heading + optional link
├─────────────────────────────────┤
│ (본문 슬롯 — 목록 / 폼 / 안내)   │
└─────────────────────────────────┘
bg-surface · border 1px · radius 12 · padding 16(모바일)/20(데스크톱)
```
variant: `default` / `placeholder`(점선 border, 배경 없음, text-faint)

### 4.2. ListItem

일정표 행, 자료 행, 기록 행이 전부 이것 하나다.

```
┌──────────────────────────────────────────┐
│ [W03]  제목이 여기에 들어간다      [배지] │
│        메타 · 메타 · 메타              › │
└──────────────────────────────────────────┘
좌: 고정폭 리드(주차/타입 배지) 44px
중: 제목(body, 1줄 말줄임) + 메타(meta)
우: 상태 배지 + chevron
높이 최소 56 / 탭 영역은 행 전체
```

### 4.3. Badge

색+텍스트를 항상 병기한다(색만으로 의미를 전달하지 않는다 — 접근성).

| 종류 | 표기 | 색 |
| --- | --- | --- |
| 주차 | `W03` | neutral, 현재 주차만 `--today` |
| 오늘 | `오늘` | `--today` bg-soft |
| 타입 | `과제` / `노트` | assignment / note |
| 자료 수 | `📎 2` | neutral, 0이면 렌더하지 않음 |
| 내 기록 있음 | `●` 점 1개 + a11y 텍스트 "기록 있음" | primary |
| 승인 상태 | `대기` / `승인` / `반려` | neutral / success / danger |

### 4.4. InlineComposer ★ 이 서비스의 핵심 컴포넌트

**3클릭 30초는 여기서 결정된다.** 상세 설계는 6장.

### 4.5. EmptyState

원칙 3을 강제하는 컴포넌트. **props로 `alternative`(대체 정보)와 `action`(다음 행동)을 필수로 받는다.** 둘 중 하나라도 없으면 이 컴포넌트를 쓸 수 없게 한다.

```
    (아이콘 없음 — 장식 대신 정보를 둔다)
    아직 기록이 없습니다
    ────────────────────────────
    다음 강의는 8/3(월) W04 · AI 활용 개발
    [오늘 강의에 기록 남기기]        ← action
```

### 4.6. Sheet (모바일) / Popover (데스크톱)

첨부 파일 메뉴, 기록 항목의 수정·삭제, 관리자 일정 선택에 쓴다. 같은 내용을 폭에 따라 다른 그릇에 담는다.

### 5.2. 일정표 — `/timeline`

23주 전체. 목적은 **훑어보기와 과거 자료 발굴**이다.

```
┌───────────────────────────────┐
│ 일정표                         │
│ ┌───────────────────────────┐ │
│ │ W01 W02 [W03] W04 W05 ... │ │ ← 주차 점프 칩 (가로 스크롤, 현재 주차 중앙 고정)
│ └───────────────────────────┘ │
│                                │
│ W01  7/14 – 7/18               │ ← 주차 헤더 (sticky)
│  ┌──────────────────────────┐ │
│  │ 월 7/14 팀빌딩, Git   📎1 │ │

│  │ 금 7/31 DB 설계           │ │
│  └──────────────────────────┘ │
└───────────────────────────────┘
```

**자료 배지(📎2)는 별도 탭 타깃이다.** 행 전체를 누르면 일정 상세로 이동하지만, 배지만 누르면 **그 자리에서 자료 목록이 펼쳐진다.**

```
  │ 화 7/28 Java/Spring 📎2 ● │
  │  └ Spring DI 개요.pdf   ↓ │  ← 아코디언 확장
  │  └ 실습 저장소          ↗ │
```

> 이 아코디언이 기획서 3.2의 **"지난 자료 찾기 2클릭"** 을 실제로 달성시키는 장치다. 상세로 들어가는 방식은 (탭 1 + 행 1 + 다운로드 1) = 3클릭이 되어 기준을 못 맞춘다.

- 진입 시 스크롤 위치: **오늘 주차가 화면 상단에서 1/3 지점**에 오도록 자동 스크롤(원칙 4). 스크롤 복원은 하지 않는다 — 항상 오늘로 돌아온다.
- 지난 주차는 텍스트 대비를 낮추지 **않는다.** 포트폴리오 축이라 과거가 열등해 보이면 안 된다. 대신 오늘만 강조한다.
- `hasMyRecord` = `●` 점. **"이 날 나는 뭔가 남겼다"가 23주 통째로 한눈에 보이는 것**이 이 화면의 숨은 가치다(기록 동기).

### 5.3. 일정 상세 — `/timeline/:id`

섹션 누적형. 기록 등록의 정식 지점.

```
┌───────────────────────────────┐
│ ‹ 일정표                       │
│                                │
│ W03 · 7월 30일 목요일    [오늘]│
│ Java/Spring 기초               │
│ 권기창                         │
│                                │
│ ── 강의자료 2 ───────────────  │ ← 섹션 1
│  📄 Spring DI 개요.pdf         │
│     PDF · 2.1MB · 권기창    ↓ │
│  🔗 실습 코드 저장소           │
│     링크 · 슬랙 원본        ↗ │
│                                │
│ ── 내 기록 2 ────────────────  │ ← 섹션 2
│  ┌───────────────────────────┐│
│  │ + 이 강의에 기록 남기기    ││ ← 컴포저를 목록 '위'에 둔다
│  └───────────────────────────┘│
│  [노트] DI 3가지 주입 방식     │
│         오늘 21:10       📎1 ⋯│
│  [과제] 실습 과제 제출         │
│         오늘 18:02          ⋯│

```

- **컴포저를 목록 위에 두는 이유** — 기록이 20건 쌓여도 등록 버튼까지 스크롤하지 않는다. 등록 비용이 데이터 양에 비례하면 안 된다.
- 자료 행은 kind에 따라 아이콘·액션이 다르다. `FILE` → `↓ 다운로드`, `LINK` → `↗ 새 탭`. **링크 기반(기획서 10.3 C안)이므로 출처가 슬랙이면 "슬랙 원본"을 메타에 명시**해 어디로 가는지 예고한다.
- 기록 행 우측 `⋯` → Sheet(모바일)/Popover(데스크톱): 수정 · 파일 추가 · 삭제.
- 삭제는 확인 다이얼로그 대신 **즉시 삭제 + 5초 "실행 취소" 토스트**. 소프트 삭제(`deleted_at`)라 안전하고, 확인 모달은 마찰이다.

포트폴리오 뷰. **"내가 23주 동안 뭘 했는지"가 한 화면에서 읽혀야 한다.**

```
┌───────────────────────────────┐
│ 내 기록                        │
│ ┌───────────────────────────┐ │
│ │ 3주차 진행 중 · 총 12건    │ │ ← 요약 스트립

│ └───────────────────────────┘ │
│                                │
│ [전체] 과제  노트     최신순 ⇅ │ ← 필터 칩 + 정렬 토글
│                                │
│ W03 ────────────────────────   │ ← 주차 그룹 헤더 (sticky)
```

- 빈 상태: "아직 기록이 없습니다 / 오늘 강의는 Java/Spring 기초입니다" + `[오늘 강의에 첫 기록 남기기]` → 홈 컴포저로 이동.

## 6. InlineComposer — 3클릭 30초의 실체

### 6.1. 상태 전이

```
[접힘]
┌──────────────────────────────────┐
│  + 이 강의에 기록 남기기          │   높이 44 · 점선 border · text-muted
└──────────────────────────────────┘
        ↓ 탭 (클릭 1)
[펼침]
┌──────────────────────────────────┐
│ W03 · Java/Spring 기초 에 저장됩니다│ ← 분류 대신 '확인 라벨' (원칙 1)
│                                   │
│  ( 노트 ) ( 과제 )                │ ← 세그먼트, 노트 기본 선택
│  ┌──────────────────────────────┐│
│  │ 제목                          ││ ← autofocus, 필수, 단일행
│  └──────────────────────────────┘│
│  ┌──────────────────────────────┐│
│  │ 내용 (선택)                   ││ ← 자동 높이, 3행부터 시작
│  └──────────────────────────────┘│
│  📎 파일   🔗 링크                │ ← 선택 기능은 텍스트 버튼으로 접어둠
│                     [취소] [저장] │ ← 제목 있으면 활성
└──────────────────────────────────┘
        ↓ 저장 (클릭 2)
[저장 완료] 폼 접힘 → 목록 최상단에 항목 삽입 (1.2s 하이라이트)
           토스트: "기록했습니다 · 실행 취소"
```

### 6.2. 클릭 수 검증 (기획서 3.2)

| 시나리오 | 클릭 | 기준 | 판정 |
| --- | --- | --- | --- |
| 노트 1건 (홈에서) | ① 컴포저 열기 → 제목 입력 → ② 저장 | 3클릭 | **2클릭** ✅ |
| 과제 1건 | ① 열기 → ② `과제` 탭 → 제목 → ③ 저장 | 3클릭 | **3클릭** ✅ |
| 파일 첨부 기록 | ① 열기 → ② `📎 파일` → ③ 파일 선택 → ④ 열기 → 제목 → ⑤ 저장 | 5클릭 | **5클릭** ✅ |
| 지난 자료 찾기 | ① 일정표 탭 → ② 자료 배지 (아코디언) | 2클릭 | **2클릭** ✅ |
| 분류 결정 | 없음 (타입은 기본값 있는 2지선다) | 0회 | **0회** ✅ |

> 타입 세그먼트를 "분류 0회"에 위배되지 않는다고 보는 근거: **선택하지 않아도 저장이 완료되고**, 선택지가 2개이며, 나중에 바꿀 수 있다. 사용자가 "어디에 넣을지 고민"하는 결정이 아니다.

### 6.3. 모바일 전용 규칙

- 키보드가 올라오면 **저장 버튼이 키보드 바로 위에 sticky**로 붙는다. 키보드를 내렸다 저장하는 동작이 들어가면 30초가 깨진다.
- 제목 입력에서 `Enter` = 저장(단일행이므로). 내용 입력에서 `Enter` = 줄바꿈, `⌘/Ctrl+Enter` = 저장.
- 컴포저를 열면 **폼 상단이 화면 상단에 오도록 스크롤**한다. 폼이 키보드에 가려지면 안 된다.
- 한 손 조작: 컴포저의 모든 탭 타깃이 화면 하단 60% 안에 오도록 배치한다.

### 6.4. 첨부 파일 처리

API는 "기록 생성 → 첨부 업로드" 2단계지만(기획서 11.3), **UI에서는 한 번의 저장으로 보인다.**

```
저장 클릭
  → POST /submissions          (즉시, 텍스트만)
  → 목록에 항목 삽입 + "업로드 중 1/1 ▓▓▓░░ 40%"
  → POST /submissions/{id}/attachments  (백그라운드)
  → 진행 바 사라지고 📎1 배지로 확정
```

- 업로드가 실패해도 **기록 자체는 이미 저장되어 있다.** 항목에 `⚠ 첨부 실패 · 다시 시도` 인라인 표시. 텍스트를 다시 입력하게 만들지 않는다.
- 클라이언트 사전 검증: 20MB 초과 / 5개 초과 / 허용 외 확장자는 **선택 즉시** 안내하고 서버로 보내지 않는다.
- 파일 칩: `Spring실습.pdf 1.2MB ✕`

### 6.5. 초안 보존 (오프라인 대비)

수업 중 네트워크는 불안정하다. 컴포저 입력값은 **키 입력 300ms 후 localStorage에 `draft:schedule:{id}` 로 저장**하고, 저장 성공 시 지운다. 페이지를 이탈했다 돌아오면 "작성 중이던 기록이 있습니다 · 이어서 쓰기"로 복구한다.

> 이건 기능 추가가 아니라 **마찰 제거**다. 한 번이라도 쓰던 글이 날아가면 그 사용자는 다시 안 쓴다.

## 9. 접근성

- 대비 4.5:1 이상(`--text-muted #737373` on `#FFFFFF` = 4.7:1 ✅, `--text-faint`는 비활성 텍스트에만).
- 색만으로 의미 전달 금지 — `●` 기록 표식에는 `aria-label="기록 있음"`, 배지는 텍스트 병기.

- 폼 오류는 필드 바로 아래 텍스트 + `aria-describedby`. 색만으로 표시하지 않는다.
- 터치 타깃 44×44, 인접 타깃 간 최소 8px(일정표 행 vs 자료 배지가 특히 위험).

## 11. 프로토타입 제작 순서

Pencil → Figma → 프론트 순으로 갈 때, **한 단계에서 확정한 것을 다음 단계에서 다시 정하지 않도록** 순서를 고정한다.

### Step 1. 토큰 (Pencil `set_variables` / Figma Variables)
3장의 컬러·타이포·간격을 **변수로 먼저 등록.** 이후 어떤 요소도 raw 값을 쓰지 않는다. 여기서 손을 대면 나중에 전체 재작업이다.

### Step 2. 공용 컴포넌트 6종
`Card` / `ListItem` / `Badge` / `InlineComposer` / `EmptyState` / `Sheet`.
InlineComposer는 **접힘·펼침·저장중·오류 4개 variant를 모두 만든다.** 이게 이 서비스의 심장이라 상태를 안 그리면 프로토타입의 의미가 없다.

### Step 3. 모바일 375px 5화면
`홈 → 일정표 → 일정 상세 → 내 기록 → 로그인`. **모바일을 먼저 완성한다**(원칙 5). 데스크톱부터 그리면 모바일이 축소판이 된다.

### Step 4. 인터랙션 연결 (여기까지가 최소 검증 단위)
아래 3개 플로우만 클릭 가능하게 연결하면 사용성 테스트가 가능하다.
1. 홈 → 컴포저 열기 → 입력 → 저장 → 목록 반영
2. 일정표 → 자료 배지 → 아코디언 → 다운로드
3. 내 기록 → 필터 → 항목 → 일정 상세

### Step 5. 데스크톱 1440px 확장
사이드바 + 2열 그리드. 모바일에서 확정한 컴포넌트를 재배치만 한다.

### Step 6. 관리자 2화면
승인함 · 일정 관리. 데스크톱만.

### Step 7. 프론트 이식
현재 코드(`frontend/src/`)는 0단계 스캐폴딩 상태다. 이식 순서:
```
index.css @theme 에 토큰 등록
  → components/ 6종
  → pages/Home · Timeline · ScheduleDetail · MyRecords 교체
  → lib/mock.ts 로 API 계약(기획서 11장) mock → 백엔드 대기 없이 완주
```

## 12. 프로토타입으로 검증할 것

만드는 게 목적이 아니라 **고칠 지점을 찾는 게** 목적이다. 동료 2~3인에게 아래를 시키고 **말리지 않고 관찰한다.**

| 과업 | 측정 | 합격선 |
| --- | --- | --- |
| "오늘 배운 걸 노트로 남겨보세요" (설명 없이) | 첫 탭까지 걸린 시간, 총 클릭 | 5초 내 시작 · 3클릭 |
| "지난주 Git 자료를 찾아 열어보세요" | 클릭 수, 경로 이탈 횟수 | 2클릭 · 이탈 0 |
| "과제에 파일을 첨부해 제출하세요" | 클릭 수, 첨부 버튼 발견 시간 | 5클릭 · 3초 내 발견 |
| 홈 진입 3초 후 "지금 뭐가 보이나요?" | 오늘 강의를 먼저 말하는가 | 3명 중 3명 |
| 아무 설명 없이 1분 탐색 | "이게 뭐 하는 서비스 같나요?" | "학습 기록"이 나오는가 |

**관찰 포인트(수치로 안 잡히는 것)**
- 컴포저를 열고 **멈칫하는가.** 멈칫하면 "무엇을 써야 할지" 안내가 부족한 것 → placeholder 문구를 고친다.
- 타입(과제/노트)을 **고민하는가.** 고민하면 분류 0회가 깨진 것 → 기본값 유지가 옳았는지 재검토.
- 일정표에서 **자료 배지를 누르는가, 행을 누르는가.** 행을 누르면 배지가 눌러 보이지 않는 것 → 배지 어포던스 강화.
- 저장 후 **"됐나?" 하고 다시 확인하는가.** 확인하면 피드백이 약한 것 → 하이라이트를 강화한다.
